# Этап 5: генератор и независимый валидатор

Реализация паспортов З4/З5 ТЗ v0.9. Основной DOCX, ID требований и очереди не меняются. Нормативные основания: GEN-001–006, ENG-007–009/012/014, REQ-004/006, VER-002, RULE-001–003/005, CAL/HRS, UX-009/015. RULE-004, SUB, RPR, CMP, публикация и экспорт не входят в этот модуль.

## Поддержанный объём

Расчёт охватывает явно выбранные группы, один семестр и разрешённые кабинеты в одном контексте года/вида данных. Включаются **все потребности этого семестра выбранных групп**, а не только уже размещённые предметы. Часы берутся из подтверждённой семестровой потребности S1; недельные значения не превращаются в семестровые и не трактуются как недельные лимиты без соответствующего правила.

Поддерживаются целые группы, одно подтверждённое назначение преподавателя на потребность, эксклюзивные кабинеты и единый подтверждённый часовой пояс. Неоднозначные строки S1, подгруппы, совместные назначения, неизвестные часы, календарь, доступность или свойства помещения блокируют запуск. Значения и подтверждения сохраняют источник и автора.

Справочник `planning_rules` — ввод подтверждённых данных ядра, предусмотренных RULE-003/005, а не отложенный модуль пожеланий/заявок. `admin` заполняет размеры групп, вместимость и признаки оборудования кабинетов, требования предметов, окна доступности преподавателей/кабинетов и известную внешнюю занятость. Подтверждение относится ко всему документу и его источнику. Пустой список требований означает проверенное отсутствие специальных требований; неизвестное нельзя подтверждать таким способом. Неизвестные числовые значения остаются NULL.

Окна задаются датами, днями недели и временем; вне их ресурс недоступен. Соприкасающиеся/перекрывающиеся окна объединяются при проверке покрытия интервала. Известная внешняя занятость исключает пересекающиеся размещения. Неполнота внешних сведений явно отмечается в результате; независимая допустимость внутри заявленного профиля не означает проверку всех отделений колледжа.

## Модель допустимости

Для каждой потребности, разрешённой конкретной даты, интервала звонков и подходящего кабинета создаётся булева переменная `x`. В домен входят только подтверждённые календарные даты нужного семестра, покрытые доступностью преподавателя/кабинета, без известной внешней занятости, с достаточной вместимостью и требуемыми признаками оборудования.

- `sum(длительность_в_минутах × x) = подтверждённые_семестровые_минуты` для каждой потребности.
- `NoOverlap` для преподавателя, всей группы и эксклюзивного кабинета на каждой конкретной дате; интервалы `[начало, конец)`.
- Закреплённое активное проведение обязательно; закреплённая отмена сохраняется и исключает восстановление того же назначения под новым ID.
- Идентичность преподавателя берётся из подтверждённого назначения S1. Замена преподавателя и вывод компетенции по ФИО отсутствуют.

Решатель OR-Tools CP-SAT решает задачу допустимости. Целевой функции качества нет: интерфейс показывает `feasible`, в том числе при исходном статусе CP-SAT `OPTIMAL`. Это не утверждение об удобстве, равномерности недель или лучшем расписании. Даты внутри семестра могут распределяться по-разному.

Диагностика сохраняет подтверждённую потребность, источник и число допустимых размещений. `infeasible` относится к конечной модели с выбранными ресурсами и закреплениями; диагностический перечень не выдаётся за минимальное противоречивое ядро.

## Задачи, процессы и лимиты

API сохраняет `SolverJob` и неизменяемый снимок: назначения/потребности, календарные документы, выбранные комнаты, условия, закрепления, область, ревизии и версию правил. Предпросмотр выдаёт токен этих зависимостей; устаревший токен отклоняется до постановки в очередь.

Работник запускается командой проекта в отдельном процессе. Один session advisory lock PostgreSQL допускает одного работника на БД. Короткая транзакция забирает задачу через `FOR UPDATE SKIP LOCKED`; поиск идёт в дочернем процессе без удержания транзакции или HTTP-запроса. После перезапуска работник помечает прерванные `running` как `failed / WORKER_INTERRUPTED`, сохраняя снимки.

| Ограничение | Реализация |
|---|---|
| Очередь | До 8 активных задач на БД; одна активная на контекст; атомарный приём через отдельную advisory-блокировку |
| Выбор | До 20 групп, 30 кабинетов и 200 потребностей |
| Модель | До 20 000 булевых кандидатов; превышение — ошибка размера, не доказанная невозможность |
| Результат | До 10 000 проведений с учётом сохранённых отмен и до 200 серий, совместимых с редактором |
| Поиск | 1–30 с, один поток CP-SAT, seed 0; параметры сохраняются |
| Процесс | Общий бюджет поиска плюс 30 с на подготовку/запуск; RSS отслеживается каждые 0,1 с, процесс останавливается после наблюдаемого превышения 768 MiB |
| API | Тело до 128 KiB; списки задач 30, отчётов по версии 10; диагностика до 200 записей каждого вида с явным признаком сокращения |

768 MiB — **предположение настройки локального стенда** с запасом относительно зафиксированного замера, а не подтверждённая вместимость колледжа. Мониторинг RSS является наблюдаемым пределом с интервалом опроса, а не жёсткой резервацией ОС. Превышение общего времени/памяти даёт отдельную ошибку процесса. Лимит поиска без решения даёт `time_limit_without_solution`; отмена — `cancelled`; `MODEL_INVALID` — `failed`.

Интерфейс показывает фактические этап и прошедшее время, время последнего успешного опроса, статус; исходный статус решателя хранится в сохранённом результате. Процент завершения не вычисляется. После обновления страницы задача восстанавливается по ID; в браузере хранится только ID, не учётные данные или снимок.

## Сохранение и устаревание

Изменение ревизии контекста S1, выбранного календаря/кабинета, условий, базового черновика или версии правил делает расчёт `stale`. Исходный статус выполнения хранится отдельно. Устаревший результат не создаёт черновик; поддержан повторный расчёт.

При актуальном допустимом результате одна транзакция блокирует область → контекст → задачу, повторно проверяет права и активность автора, запускает независимую проверку и сохраняет новый черновик, его ревизию и связанный отчёт. Повтор завершения той же задачи не создаёт ещё один черновик. Ошибка до commit откатывает все новые записи. Исходный черновик и его остальные занятия не изменяются; автоматического утверждения/публикации нет.

Из базового черновика берутся только закреплённые проведения выбранных групп/семестра. Остальные занятия составляются заново в новом результате; это не ограниченный перерасчёт RPR. Нельзя потерять активное закрепление или восстановить закреплённую отмену.

## Независимая проверка ENG-007

`domain/validation.py` получает обычные значения снимка и проведений; не импортирует HTTP, ORM, решатель или его домен кандидатов. По каждому проведению заново проверяются формат, уникальность ID, подтверждённое назначение и отображаемые значения источника, семестр, дата, сетка звонков, кабинет, доступность, оборудование, вместимость и известная внешняя занятость. По активным проведениям заново строятся интервалы занятости и суммы минут; отмены не добавляют часы.

Полнота проверяется по всем потребностям выбранной области, включая ни разу не размещённые. Закрепления сравниваются с исходным снимком. Статус и таблица занятости решателя не используются как доказательство.

Отчёт содержит точные ID/ревизию/снимок, контекст и семестр, ошибки/вопросы, оба события и даты конфликтов, ресурсы, часы и остаток. Исторический отчёт не меняет расписание. Изменение черновика или зависимостей помечает отчёт устаревшим; отчёт результата задачи также не разрешает изменённую ревизию черновика.

Быстрый поиск сравнивается с простым попарным эталоном на малых случайных/граничных наборах. При превышении лимита диагностики поиск прекращается с `conflicts_truncated=true`; усечённый отчёт не бывает успешным. Замеры времени/памяти приведены отдельно. Публикационный модуль должен заново вызывать проверку точной ревизии и актуальной общей занятости в своей защищённой транзакции.

## Права и API

| Действие | admin | scheduler | approver | teacher/student |
|---|---|---|---|---|
| Данные условий/справочников своей области | Да | Да | Да | Нет |
| Изменить и подтвердить условия | Да | Нет | Нет | Нет |
| Предпросмотр, запуск, отмена | Нет | Да | Нет | Нет |
| Читать задачи и отчёты, проверить черновик | Нет | Да | Да | Нет |
| Читать черновики через экран условий | Нет | Да | Да | Нет |

Все закрытые действия проверяют серверные права и область из загруженных объектов; CSRF/Origin, строгие DTO, ограничения тела и аудит сохраняются. Отзыв прав автора до завершения блокирует сохранение результата.

- `GET /api/scopes/{scope}/planning-data` — разрешённые контексты/ресурсы/условия.
- `POST /api/planning-contexts/{context}/rules` — `expected_revision`, документ условий; история ревизий.
- `POST /api/scopes/{scope}/generation-preview` — контекст, группы, комнаты, семестр, необязательная база; готовность и токен.
- `POST /api/scopes/{scope}/solver-jobs` — тот же выбор, токен и лимит поиска.
- `GET /api/scopes/{scope}/solver-jobs`, `GET /api/solver-jobs/{id}` — разрешённые задачи и статус.
- `POST /api/solver-jobs/{id}/cancel` — запрос отмены; безопасен при повторе.
- `POST /api/drafts/{id}/validate` — выбранная ревизия, группы/комнаты/семестр.
- `GET /api/drafts/{id}/validations` — исторические отчёты с вычисленной актуальностью.

## Решения архитектуры и границы

1. **Модель и валидатор разделены:** инфраструктурный адаптер OR-Tools строит ограничения; чистый валидатор восстанавливает факты из событий. Общими остаются значения правил календаря/доступности/единиц.
2. **Одна локальная очередь:** PostgreSQL вместо дополнительного брокера; один работник и ограниченный дочерний процесс достаточны для текущего профиля. API не запускает поиск в своём потоке.
3. **Условия отдельным ревизионным документом:** обязательные входы ядра вводятся без переноса заявок/пожеланий из очереди 2. Новые элементы справочников появляются в форме как неизвестные и требуют повторного подтверждения.
4. **Безопасные отказы Windows:** закрытие pipe обрабатывается без потери полученного результата; `status_name` OR-Tools 9.15 вызывается с явным исходным статусом. Пароли, тексты исходных строк и нативные исключения не пишутся в диагностику работника.
5. **Остальные этапы:** согласование, атомарная публикация общих ресурсов, неизменяемые опубликованные версии и XLSX остаются отдельными задачами. Регистрация/восстановление, пожелания, замены, перерасчёт, сравнение, RU/EN сохраняют согласованные очереди.

Для мамы: «Решатель выбирает размещения по подтверждённым ограничениям. Второй модуль независимо пересчитывает даты, занятость и часы. Если данных не хватает или они изменились, программа честно блокирует запуск или показывает устаревший результат». Код для объяснения: `solver.build_model`, `validation.validate_schedule`, `generation.finish`.
