# Этап 5 — отчёт испытаний З4/З5

Дата: 21.10.2026. Постановка: ТЗ v0.9, паспорта З4 «Генератор» и З5 «Независимый валидатор». База: `72714ab2b02d9da36307c934e204a71f38a87a07`. Сборка однозначно связана с исходниками через SHA-256 и определение отпечатка в `stage-5-planning-acceptance.json`.

Все новые наборы синтетические. Книги колледжа не включены в коммит и не применены для демонстрации. Доступность, размеры групп, свойства кабинетов и потребности контрольных наборов не являются фактами колледжа.

## Автоматические проверки

| Проверка | Фактический результат |
|---|---|

| Предметный набор после уточнения нативного контрольного теста статусов | 33 passed, 2,00 с; продуктовый код после полного backend-прогона не менялся |
| Полный frontend: `npm test -- --reporter=dot` | 54 passed, 6,23 с |
| `npm run build` | TypeScript и Vite прошли |
| `npm run format:check` | Все проверяемые файлы соответствуют Prettier |
| Реальная миграция `0005_planning` и `alembic check` | Успешно; расхождений схемы нет |
| `pip check`, `compileall`, `git diff --check` | Успешно |

64 новых backend-теста (31 интеграционный и 33 предметных), 15 новых frontend-тестов. Остальные проверки — регрессия основы, S1, календаря и редактора.

Интеграционные тесты используют отдельную локальную БД `_test` с настоящими миграциями и транзакциями PostgreSQL. Процессный тест запускает реальный дочерний процесс с OR-Tools. Проверены очередь, параллельная постановка, отмена, авария, лимиты времени/памяти, откат до фиксации, повтор завершения, отзыв прав автора, ревизии и неизменность исходного черновика.

Нативные контрольные модели различают `UNKNOWN`, `INFEASIBLE`, `MODEL_INVALID` и `FEASIBLE`. Для получения последнего при лимите используется отдельная тестовая модель с целевой функцией и контролируемым выходом за время после первого решения; в продуктовую модель оптимизация качества не добавлена. Исходный `OPTIMAL` задачи допустимости также отображается как `feasible`.

Испорченные результаты проверяются без запуска решателя: неверные дата, время, преподаватель, отображаемый предмет, ревизия кабинета, потерянное проведение, дублированный ID, поддельный признак эксклюзивности и изменённое закрепление отвергаются. Полнота учитывает неразмещённые потребности; отмены не добавляют минуты.

Свежий отдельный интерпретатор запускает валидатор с заблокированными импортами FastAPI, SQLAlchemy и OR-Tools. Быстрый поиск конфликтов сравнивается с независимым попарным эталоном на 100 наборах по 25 событий, включая отмены, разные даты и соприкасающиеся интервалы.

| AC-009d | Must-A | Реальный работник создаёт один новый черновик и связанный независимый отчёт: `test_real_worker_creates_exactly_one_new_draft_and_independent_report`; B5-04/13 |
| AC-016b | Must-A | Испорченный результат не сохраняется как допустимый: `test_corrupt_feasible_result_is_independently_rejected_before_draft_creation`, предметные негативные тесты |

Связанные проверки календаря/часов/ресурсов подтверждены в независимом валидаторе. Для AC-035a проверены привязка отчёта к ревизии и stale; публикационное применение остаётся за модулем версий. Новых AC не добавлено.

## Замеры и готовность

Файл `stage-5-planning-benchmark.json` сохраняет реальный стенд и версии: Windows 11 AMD64, Python 3.12.14, OR-Tools 9.15.6755, 12 логических CPU, около 16 GiB ОЗУ. Набор: 16 групп, 32 потребности, 8 преподавателей, 4 кабинета, 5 120 кандидатов.

- Поиск с бюджетом 30 с: `feasible`, 128 проведений, 2,646824 с полного вызова; исходный статус `OPTIMAL` относится к допустимости.
- Независимая проверка отдельного детерминированного контроля из 128 проведений: допустимо и полно, 0,020482 с.
- Наблюдаемый RSS всего процесса: 198 365 184 байт (около 189,2 MiB), выборка каждые 0,01 с; Python-память проверки отдельно 158 481 байт.

Это фактический инженерный замер, а не обещание времени на любой книге колледжа или проверка всех целей NFR-004. Короткий контроль с лимитом 2 с ранее завершился без решения; он не интерпретировался как невозможность.
