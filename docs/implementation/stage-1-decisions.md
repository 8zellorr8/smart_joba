# Решения первого этапа

Дата: 21.10.2026. Основание: ТЗ v0.9 и разрешение пользователя реализовать локальный каркас, БД, вход, подготовленные аккаунты, права и KK-интерфейс.

| Решение | Причина и последствия |
|---|---|
| React + TypeScript; FastAPI; PostgreSQL; один сервер для интерфейса и API | Соответствует выбранной архитектуре и работает без внешних сервисов. Слои backend разделены по ответственности. |
| Отдельный PostgreSQL на 55432 | Используются установленные бинарники и собственный кластер `.local`. Служба PostgreSQL компьютера не изменяется. Учётная запись приложения не является суперпользователем. |
| Миграции Alembic, отдельная тестовая БД | Схема приложения создаётся миграцией, а не при старте API. Тесты допускают только loopback-базу с суффиксом `_test`. |
| Непрозрачные серверные сессии | В БД только SHA-256 токена; выход, истечение и отключение аккаунта проверяются сервером. Роли заново читаются при каждом запросе. |
| Подписанный CSRF, привязанный к сессии; Origin/Host; HttpOnly/SameSite | Изменяющие запросы требуют токена и допустимого Origin. Интерфейс обновляет истёкший CSRF перед повтором выхода. HTTP cookie допускается только локально. |
| Матрица действий по роли и scope, отдельный `can_publish` | Администратор не получает автоматического разрешения публикации. Связи читателей заданы назначениями в БД; демосвязи синтетические. |
| Пять аккаунтов через seed, случайные пароли | Публичных паролей по умолчанию нет. Повтор seed не меняет пароли и назначения. Регистрация и восстановление пароля не входят в этап. |
| Ограничение входа по идентификатору и IP в PostgreSQL | Счётчики работают между параллельными запросами. Неизвестный аккаунт и неверный пароль имеют одинаковую публичную ошибку. |
| Резервный маршрут утверждения отвечает только 403/501 | Проверяет отрицательное серверное разрешение. Реального утверждения пока нет; AC-010a остаётся частичным. В будущем scope определяется по загруженной версии, а не query-параметру. |
| Локальный COMSPEC wrapper с `cmd /d` | На этом компьютере cmd AutoRun печатает кодовую страницу и ломает проверку версии `initdb`. Wrapper применяется только к дочерним процессам проекта; реестр и системный cmd не меняются. |

Таблицы версий, календаря, занятий и нагрузки будут добавляться следующими миграциями. Полномочие в матрице обозначает разрешённое действие будущего модуля, а не наличие его реализации.

Сохраняются обязательные правила следующих этапов: REQ-006, VER-001/002, GEN-004, ENG-007, IMP-007. Их наличие в ТЗ не является результатом испытания текущего кода.

## Дополнение этапа 6: публикация и чтение снимков

Дата решения: 21.10.2026. Исходная таблица выше фиксирует первый этап; временный маршрут утверждения теперь заменён реальным модулем З7. Состояния, контракты и общий порядок операции определены в [контракте этапа 6](stage-6-publication-contract.md).

**Проблема.** Блокировка своего черновика или отделения не исключает конкурентную публикацию другого профиля с тем же ресурсом. Несколько запросов после потери связи не должны создавать несколько публикаций; читатель не должен смешивать прежний снимок с новым указателем.

**Рассмотрены:** общая транзакционная advisory-блокировка; упорядоченные блокировки каждого ресурса/даты; SERIALIZABLE с ограниченным повтором. Первый вариант выбран для локального MVP: у всех публикационных записей одна граница сериализации, а доказательство безопасности не зависит от полного перечня потенциальных пересечений.

**Решение.** `PublicationService` — единственный прикладной писатель указателей; до блокировок области он получает общую блокировку PostgreSQL. Проверка и запись снимка выполняются в одной транзакции с обычными ревизионными и серверными проверками. Уникальные ограничения сохраняют один результат ключа и один указатель профиля, триггеры защищают неизменяемые записи. Счётчик номеров версий отделён от ревизий учебных входов.

Читатель использует READ ONLY / REPEATABLE READ. Альтернатива с общей разделяемой блокировкой на каждое чтение задерживала бы публикацию длинным просмотром; MVCC даёт цельный снимок без такого ожидания. Служебная и читательская проекции разделены по разрешённым полям.

**Последствия.** Публикации сериализуются; при конкуренции возможен контролируемый `PUBLICATION_BUSY`. Общность ресурса определяется подтверждённым UUID, а не именем; предположение об области колледжа и границы внешней занятости зафиксированы в контракте. Автоматическое разделение/слияние действующих профилей не вводится.

**Проверка.** Реальный PostgreSQL: гонка конфликтующих профилей, параллельный повтор ключа, откат после смены указателя, исчерпание ожидания и публикация в середине читательского запроса. Предметный индекс проверен попарным случайным эталоном и границами часовых поясов. Результаты и ограничения: [отчёт этапа 6](stage-6-publication-test-report.md).
